# inbox — 未审阅的知识候选

agent 在需求过程中自动沉淀的教训落在这里，`trust: L2`。

**`L2` 内容不得作为实现依据。** 它没有经过人工核对，可能来自一次偶发环境问题、也可能是模型的错误归因。

## 审阅节奏

每 5~10 个需求审一次，每条只有三种结局：

1. **合并** — 内容归入已有主库卡片（`map/` / `pitfalls/` / `decisions/`）。
2. **升级** — 补齐 front-matter 与证据，移入主库成为独立卡，`trust` 改 `L1`。
3. **丢弃** — 无证据、无复发风险、或只是一次性环境问题。

不积压：候选堆得越多，越没人会去审，最后整个 inbox 变成噪声。

## 候选卡最低要求

```yaml
---
trust: L2
anchors:
  - <相关文件路径>
verified_commit: <当时的 HEAD>
verified_at: <日期>
supersedes: null
---
```

正文至少要有：**现象**、**当时的归因**、**证据或复现线索**。缺证据的条目在审阅时一律丢弃，别指望日后补。
