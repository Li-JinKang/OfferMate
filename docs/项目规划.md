# OfferMate 项目规划文档

> 一款**纯端侧** Android 应用：用户把牛客 / 小红书的面经**链接**分享/粘贴进来，App 在设备本地读取帖子内容，用 AI **分析其中的面试题**，筛选出**与用户简历相关**的题目并生成参考答案，最后通过"先答后看"的刷题机制帮助复习。

---

## 1. 产品定位与核心能力

### 1.1 一句话定位
"分享一个面经链接 → App 读取内容 → AI 挑出与我简历相关的题 → 生成答案 → 刷题自测。"

### 1.2 核心能力（重要：以"分析"为核心，不是"出题"）
本应用的核心**不是**凭空生成题目，而是：
1. **读取**：从用户分享的链接中提取面经帖子的文本内容。
2. **抽取**：从帖子文本中识别出一道道离散的面试题。
3. **匹配**：结合用户简历，判断每道题与用户背景（岗位/技术栈/项目）的相关性并排序/筛选。
4. **作答**：为相关题目生成参考答案（可结合简历做个性化）。
5. **复习**：进入刷题模式，题目与答案分离，自评掌握度。

### 1.3 三条已确认的基本决策
- ✅ 内容来源 = **用户分享/粘贴的链接**（不做后台批量爬虫）。
- ✅ 核心 = **分析已有题目 + 简历匹配 + 生成答案**（非题目生成器）。
- ✅ 形态 = **完全端侧应用，无自建后端**。

### 1.4 MVP 范围
- 通过"分享到 App"或"粘贴链接"导入面经。
- 端侧读取链接内容（先重点保证牛客，小红书尽力而为，见第 3 节）。
- 简历导入（先支持 PDF + 纯文本）。
- AI：抽取题目 → 简历相关性筛选 → 生成答案。
- 刷题机制（答案隐藏 + 自评）。
- 本地存储全部数据。

## 2. 关键约束：无后端下的 AI 密钥问题（务必先读）

"完全端侧、无后端"与"调用大模型"存在天然矛盾：**大模型 API Key 一旦硬编码进 APK 就会泄露、被盗刷**。在无后端前提下，只有两条可行路线：

### 方案 A：自带密钥（BYOK，Bring Your Own Key）——推荐
- 用户在"设置"里填入自己的大模型 API Key（如 DeepSeek / 通义千问）。
- Key 用 `EncryptedSharedPreferences` 加密存储在本地，App 直接从设备调用模型接口。
- 优点：无需后端、质量高（用云端强模型）、成本由用户自担、开发者无密钥风险。
- 缺点：有一定使用门槛（需用户自己申请 Key）。适合工具型/面向技术人群的应用——正好契合求职者画像。

### 方案 B：端侧本地模型（离线推理）——可选/补充
- 用 MediaPipe LLM Inference / MLC-LLM / llama.cpp，跑小参数模型（如 Gemma、Qwen 小模型）。
- 优点：真正零密钥、离线、隐私最好。
- 缺点：模型体积大（数百 MB~GB）、手机上速度慢、对"中文面试题分析+作答"这类任务质量有限。**MVP 不建议作为主力**，可作为二期的离线开关。

> **结论**：MVP 采用 **方案 A（BYOK）**为主，把方案 B 作为后续的离线增强项。若坚决不想让用户填 Key，则只能走方案 B 并接受质量/性能折损。

## 3. 关键约束：端侧读取链接内容的可行性

不同平台链接的可读性差异很大，必须实事求是：

| 平台 | 端侧读取难度 | 说明与策略 |
|------|--------------|------------|
| 牛客 | 中 | 帖子页多为可访问 HTML，可用 HTTP 抓取 + HTML 解析（Jsoup）或 WebView 渲染后取文本，成功率较高 |
| 小红书 | 高 | 强反爬、内容由 JS 动态渲染、常需登录态与签名；分享出来多为 `xhslink.com` 短链需先解析重定向 |

### 3.1 端侧读取的技术路线（组合使用）
1. **短链解析**：用 OkHttp 跟随重定向，把 `xhslink.com` 等短链还原为真实 URL。
2. **优先 WebView 渲染取文**：用一个隐藏/离屏 WebView 加载页面，`onPageFinished` 后注入 JS 提取正文。
   - 内置 **Readability.js**（Mozilla 的正文提取库，作为 assets 打包）注入页面，抽取主要文章内容；或退化为 `document.body.innerText`。
   - 因为是在**用户自己的设备、用户自己的浏览环境**下加载，更接近"用户浏览"，而非服务器爬虫。
3. **降级 HTTP + Jsoup**：对牛客等静态性较强的页面，直接抓 HTML 用 Jsoup 解析，速度快。
4. **兜底手动粘贴**：当自动读取失败（尤其小红书改版/登录墙），提供"手动粘贴正文"入口，保证流程不中断。

### 3.2 诚实的预期与合规
- **小红书自动读取会不稳定**，平台改版即可能失效，需把"手动粘贴兜底"作为一等公民。
- 读取的是**用户主动分享的单篇链接**，非批量爬取；仍需遵守各平台用户协议，注明来源、不做二次分发，尊重版权与隐私。
- UI 需提示：内容归原作者/平台所有，App 仅用于个人学习整理。

## 4. 总体架构（纯端侧）

```
┌───────────────────────────────────────────────────────────────┐
│                        Android App（端侧）                       │
│                                                                 │
│  UI 层 (Compose + Material 3)                                   │
│    分享/粘贴导入 · 简历管理 · 题目列表 · 刷题卡片 · 设置(填Key)     │
│                          │                                       │
│  ViewModel (MVVM / UDF)  │                                       │
│                          ▼                                       │
│  Repository ── 聚合以下能力：                                     │
│    ├─ ContentReader   (WebView/Jsoup 读取链接正文 + Readability) │
│    ├─ ResumeParser    (端侧 PDF/文本解析)                        │
│    ├─ AiClient        (直连 LLM: 抽题→相关性→作答；BYOK)         │
│    └─ LocalStore      (Room 数据库 + DataStore/加密存储)         │
│                                                                 │
│  外部：用户自带 Key 直连  ──HTTPS──▶  LLM Provider (DeepSeek 等)  │
└───────────────────────────────────────────────────────────────┘
```

无服务端组件，所有数据（简历、题目、答案、进度、Key）都存在设备本地。唯一的出网请求是：读取用户分享的链接、以及用用户 Key 调用 LLM。

## 5. AI 处理流水线（核心）

围绕"分析已有题目"设计，分为三步 Prompt（可合并以省调用次数，但分步更可控）：

### 步骤 1：题目抽取（Extraction）
- 输入：读取到的帖子正文。
- 任务：从噪声文本（含吐槽、流程、寒暄）中识别出**离散的面试题**。
- 输出：`[{question, 原文出处片段, 初步考点标签}]`（要求 JSON 结构化输出）。

### 步骤 2：简历相关性筛选（Relevance Matching）
- 输入：步骤 1 的题目列表 + 简历结构化画像（岗位、技术栈、项目、年限）。
- 任务：为每题打相关性分（如 0-100）并给出理由，按阈值筛选/排序。
- 输出：`[{questionId, relevanceScore, reason, matchedSkills}]`。
- 说明：MVP 用 LLM 直接判分即可；题量大时二期可引入端侧 embedding 做初筛降本。

### 步骤 3：答案生成（Answering）
- 输入：筛选后的相关题目 + 简历上下文。
- 任务：生成参考答案，可结合用户项目经历做个性化回答建议；标注难度。
- 输出：`[{questionId, answer, difficulty, keyPoints}]`。

### 工程要点
- **结构化输出**：使用模型的 JSON mode / function calling，客户端做 schema 校验与容错解析。
- **分块处理**：长帖子按 token 上限切分后合并结果。
- **可插拔 Provider**：`AiClient` 做接口抽象，底层适配 DeepSeek / 通义 / GLM（多数提供兼容 OpenAI 的 `chat/completions` 接口，切换成本低）。
- **成本与速率**：本地做请求节流、结果缓存（同一链接不重复分析）。

## 6. Android 客户端技术栈

### 6.1 语言与 UI（决策点）
当前工程是 **Java + 传统 View**，且仅一个近乎空白的 `MainActivity`。绿地项目迁移成本极低，**推荐切换到 Kotlin + Jetpack Compose (Material 3)**：声明式 UI 更易实现刷题卡片的揭示/翻转动画，且现代库对 Kotlin 一等支持。（如坚持 Java + XML 亦可，下表括号给替代方案。）

### 6.2 推荐技术栈

| 领域 | 选型 | 备注 |
|------|------|------|
| 语言 | Kotlin | （或保留 Java） |
| UI | Jetpack Compose + Material 3 | （或 XML + Material Components） |
| 架构 | MVVM + 单向数据流 (UDF) | ViewModel + UiState |
| 导航 | Navigation Compose | |
| 异步 | Coroutines + Flow | （或 Executor + LiveData） |
| 依赖注入 | Hilt | |
| 网络/直连 LLM | Retrofit + OkHttp | 拦截器加 Key、日志、重试 |
| 序列化 | kotlinx.serialization / Moshi | （Java: Gson） |
| 链接内容读取 | WebView（离屏渲染）+ Jsoup + Readability.js | 见第 3 节 |
| 简历解析 | PdfBox-Android（PDF）/ 纯文本直读 | DOCX/OCR 放二期 |
| 本地数据库 | Room | 帖子、题目、答案、进度 |
| 偏好/密钥 | DataStore + EncryptedSharedPreferences | 用户 API Key 加密存储 |
| 分享接收 | Intent Filter (ACTION_SEND / VIEW) | 从牛客/小红书分享链接进来 |
| 图片加载 | Coil | |
| 后台任务 | WorkManager | 长耗时的读取+分析任务 |

### 6.3 客户端分层
```
com.jk.offermate
├── ui/            # Compose 界面 + ViewModel（import/resume/questions/quiz/settings）
├── data/
│   ├── reader/    # ContentReader：短链解析、WebView 取文、Jsoup、Readability 注入
│   ├── ai/        # AiClient：Provider 抽象 + 抽题/相关性/作答 三步编排
│   ├── resume/    # 简历解析
│   ├── local/     # Room DAO/Entity、DataStore、加密存储
│   └── repository/# Repository 聚合
├── di/            # Hilt 模块
└── share/         # Share Intent 接收与 URL 规范化
```

### 6.4 需要的工程改造
- `libs.versions.toml` 增加：Kotlin、Compose BOM、Hilt、Retrofit/OkHttp、Room、Coroutines、Navigation-Compose、Coil、DataStore、security-crypto、Jsoup、PdfBox-Android、序列化库。
- `app/build.gradle` 启用 Compose/Kotlin/Hilt/Room 插件；`compileOptions` 提升到 Java 17。
- `AndroidManifest.xml`：加 `INTERNET` 权限、`ACTION_SEND`(text/plain) 与链接 `VIEW` 的 intent-filter、启用 WebView。
- `minSdk 26` 保持不变。

## 7. 刷题（答案隐藏）机制

目标：**看到题目时不同时看到答案**，机制从简。

- **卡片式**：一屏一题，默认只显示题干、考点标签、难度、来源链接。
- **揭示答案**：答案默认隐藏，点击"显示答案" / 高斯模糊遮罩点击去模糊 / 翻卡动画，任选或组合。
- **自评掌握度**：揭示后三档 —— 不会 / 模糊 / 掌握。
- **轻量复习队列**（不引入复杂 SRS）：
  - 不会 → 进重点队列优先重现；模糊 → 正常；掌握 → 降频/移出。
- **筛选**：按考点、难度、掌握度、来源帖子过滤刷题集。

## 8. 本地数据模型（Room 草案）

```text
Resume(id, title, rawText, parsedProfileJson, createdAt)
ImportedPost(id, platform, url, resolvedUrl, title, content, readMethod, importedAt)
Question(id, postId, content, sourceSnippet, tags, difficulty,
         relevanceScore, relevanceReason, answer, answeredAt)
StudyRecord(questionId, mastery, lastReviewedAt, reviewCount)
AppSettings   // 经 DataStore/加密存储：apiKey、provider、模型名、相关性阈值
```

关系：一个 `Resume` 是分析时的上下文；一个 `ImportedPost` 抽出多个 `Question`；每个 `Question` 带相关性与答案；`StudyRecord` 记录刷题进度。

## 9. 隐私与合规

- **API Key**：仅本地加密存储，直连模型厂商，绝不外传第三方。
- **简历隐私**：全部留在设备本地；上传/解析前告知用途，支持一键删除。
- **内容版权**：仅处理用户主动分享的单篇链接，注明来源、不二次分发，尊重平台协议与作者版权。
- **AI 免责**：答案由 AI 生成，UI 标注"仅供参考，可能有误"。

|------|------|----------|
| M0 立项 | 确认技术栈、模型、BYOK 方案 | 本文档定稿 + 工程脚手架（Kotlin/Compose/Hilt） |
